# R2リンク保存の設計・運用方針

2026-09-13時点で採用した保存方針。アプリへの組み込みとR2への移行は未実施であり、以下は実装予定の動作を記載する。ローカル検証は2026-09-12に実施した。

保存方式は、**1ページの出リンク一覧を1レコードとし、日々の更新をJSONL＋gzipでまとめて保存し、分析用の最新状態をParquet＋Zstdへ整理する構成**。URL台帳・巡回キュー・小さな紹介元ホスト集計・送信待ちデータは既存のPostgreSQLを使う。R2 Standardを選ぶ。

## 設定と資料の置き場所

この文書を保存設計と運用方針の正本としてGitで管理する。実バケット名、接続設定ファイルの場所、環境ごとの設定状況は、Git管理外の `AGENTS.override.md` に記録する。アクセスキーなどの認証情報はリポジトリ外の設定ファイルに保存する。

実行コマンド、定期実行、監視、障害復旧の具体的な手順は、実装に合わせて整備する。

## レコード

JSONLでは次のJSONを1行にする。Parquetにも同じ列を持たせる。

```json
{
  "src": "https://example.org/article",
  "src_host": "example.org",
  "revision": 123456,
  "observed_at": "2026-09-12T12:00:00Z",
  "outlinks": [
    "https://example.org/about",
    "https://example.net/reference"
  ]
}
```

| 列 | 意味 |
|---|---|
| src | 現行のURLポリシーで正規化したページURL。ページの識別には完全なURLを使う |
| src_host | URLから計算するホスト名。サイト別の抽出用で、ページの識別には使わない |
| revision | PostgreSQLで観測受付時に割り当てる一意な増加番号。再送では同じ番号を保持する |
| observed_at | 取得結果の観測時刻。UTCのtimestamp。過去データで不明ならnull |
| outlinks | その観測で抽出・正規化した出リンク一覧。重複と自己リンクを除きソートする |

revisionが大きい観測を最新として採用する。これはDBが番号を割り当てた受付順という定義であり、R2への到着順やワーカーの時計では決めない。現在のlinksには観測時刻がないので、初回移行のレコードはrevision=0、observed_at=nullとする。エクスポート時刻を過去の観測時刻として入れない。

`outlinks: []` は「この観測で出リンクが0件だった」という有効な更新。最新状態へ整理した後も、このページの空レコードを残す。取得失敗や304応答を空一覧へ変換しない。削除扱いのHTTP応答等は現在のクロール方針と整合させ、単なる取得失敗と区別する。

現在のパーサーには抽出件数上限があるため、この一覧をページに実在する全リンクの完全な列挙とは定義しない。形式と正規化・抽出方針のバージョンはmanifestに記録する。

## R2のキー構成

```text
links/v1/current.json
links/v1/updates/2026/09/12/<batch-id>.jsonl.gz
links/v1/commits/<batch-id>.json
links/v1/snapshots/<generation-id>/manifest.json
links/v1/snapshots/<generation-id>/shard=ab/part-00000.parquet
```

- updatesは追加するだけの観測ファイル。同じファイルへ追記・複数ワーカーから上書きしない。
- commitsはアップロード完了の印。データのキー、SHA-256、レコード数、形式バージョンを持つ。
- snapshotsはページごとに最新観測だけを残したファイル群。SHA-256(src)の先頭2桁で256分割し、各ファイルをsrc順に並べる。ハッシュは分割先を決める用途に限定する。
- manifestには対象ファイル一覧・チェックサム・ページ数・出リンク数・取り込んだbatchの識別子を記録する。
- current.jsonは採用するmanifestのキーを指す小さなファイル。世代の全ファイルを検証してから最後に更新する。

スナップショットのURL指定読み出しは、該当する分割ファイルを計算して選べる。逆リンクや全体集計では必要な分割を横断する。読み手はmanifestのファイル一覧を使い、全世代をワイルドカードで混ぜて読まない。

## 書き込みと再送

1. クロール結果を現在と同じ規則で正規化し、既存PostgreSQLの短期送信待ち表へ1観測1行で保存する。既存のurl_referring_hosts更新と同じトランザクションにする。紹介元ホスト表の現在の観測履歴としての意味を維持する。
2. 送信処理が確定済みの行を取り出し、batch-idと対象行の集合を固定する。初期設定案は「5,000ページ・未圧縮16MiB・最古の待ち時間5分」のどれかに達したら送信。1ページの一覧は途中で分割しない。
3. JSONL＋gzipを一意なキーへPUTし、チェックサム付きの完了印を作る。確認後に、そのbatchの送信待ち行を解放する。DBの連番が一定値以下という理由だけで、未確認行を一括削除しない。
4. タイムアウト時は同じbatchを再確認・再送する。データの再生成時に内容が変わらないようにし、同じbatch-idで異なる内容が見つかったらエラーとする。

送信待ち表は全履歴の保管場所にはしない。未送信件数・容量・最古の待ち時間を計測し、上限に達したらクロール受付に制限をかけ、未保存データを黙って捨てない。R2への通信待ちは通常のクロール処理から外すが、PGへの永続記録完了は待つ。

R2は[S3 APIの条件付きPUT](https://developers.cloudflare.com/r2/api/s3/api/)と[強い整合性](https://developers.cloudflare.com/r2/reference/consistency/)を提供する。新規データのPUTはIf-None-Match、current.jsonの更新はIf-Matchを使える。これだけで複数ファイルのトランザクションが成立するわけではないため、データ→manifest→currentの公開順序を守る。currentの更新競合時は再読込し、古い世代で上書きしない。

## 最新状態への整理と読み出し

初期案では1日1回、単一の整理処理が前回スナップショットと公開済みの更新batchを結合し、srcごとに最大revisionの行を残す。開始時に処理対象のbatch一覧を固定し、その後に届いたbatchは次の処理か更新込みの読み出しで扱う。連番の最大値だけを「それ以前の全更新を取り込み済み」という印には使わない。

更新をR2へ保存する間隔とスナップショットの作成間隔は別。正常時の更新保存目標は5分程度、分析用スナップショットは1日程度の遅れを許容する初期案。用途に応じて次の2つを明示する。

| 読み方 | 対象 |
|---|---|
| スナップショット指定 | 再現可能な全体集計・PageRank。manifestを固定して読む |
| 更新込み | スナップショットと未反映の公開済みbatchを合わせて読む。管理用途のURL指定確認など |

更新込みのURL確認は、該当スナップショット分割に加えて差分ファイルも調べる。常に1回のGETだけで最新レコードが取れる設計ではない。連続した管理・分析作業では差分をローカルへキャッシュし、作業用DuckDBでまとめて読む。

最新行の選択は、必ず出リンクを行へ展開する前に行う。

```sql
-- observationsは指定スナップショットと対象batchを合わせた同じ列構成のビュー。
WITH latest_pages AS (
  SELECT *
  FROM observations
  QUALIFY row_number() OVER (
    PARTITION BY src ORDER BY revision DESC
  ) = 1
)
SELECT src, unnest(outlinks) AS dst
FROM latest_pages;
```

先にunnestすると空一覧の観測が消え、古いリンクを復活させる危険がある。同じrevisionの再送は同じ内容であることを前提とし、内容が異なる重複は受け付けない。

[DuckDB](https://duckdb.org/docs/current/data/parquet/overview)ならParquetをSQLで読み、URL指定、サイト別抽出、逆リンクの抽出、src,dst形式への展開を行える。R2との接続は[S3互換のhttpfs](https://duckdb.org/docs/current/core_extensions/httpfs/s3api)を使うか、必要なファイルをダウンロードしてローカルで読む。R2上でDuckDBが常駐する構成ではない。

## 世代保持と削除

最初は確定スナップショットを2世代保持する。更新batchは、保持する全世代がその内容を取り込み済みになり、読み手の使用期間・復旧の猶予を過ぎてから削除する。必要なbatchを単純な日数ルールだけで消さない。

manifestの取り込み済みbatch一覧は、未回収のbatchについてだけ次世代へ引き継げばよい。スナップショット本体に過去の全観測履歴や無期限の全batch一覧を蓄積しない。現行・保持世代・読取中世代が参照するファイルは削除対象から除外する。処理中に失敗した未公開ファイルも、再試行中のbatchとの照合と猶予期間を設けて回収する。

## ローカルでの確認

既存の100,000リンク×3サンプルを使い、同じページ単位レコードで比較した。過去の観測時刻はnull、revisionは0。サイズは10進MB。

| 形式 | 100,000リンクのサイズ | 用途 |
|---|---:|---|
| src,dst CSV＋gzip | 1.186〜1.204MB | 以前の容量調査の形式 |
| ページ単位JSONL＋gzip | 1.020〜1.042MB | 日々の更新ファイル。中身を確認しやすい |
| ページ単位Parquet＋Zstd | 1.214〜1.236MB | 型付きでSQLから扱う分析用スナップショット |
| 1ページ1個のgzip JSON | 2.110〜2.130MBの合計 | PUT/GET数も増えるため初期案には採用しない |

元のリンク集合との一致、URL指定の出リンク、逆リンク抽出を確認した。追加の小さな例で、古いリンクの消滅、出リンク0件、順序が逆転した配送、同じ観測の再送、空一覧のスナップショット保持も確認した。

サンプルはリンク行を抽出したものなので、各ページの全出リンクがそろっているとは限らない。サンプル間に重複もあり得る。全体の容量・所要時間・通信待ち・R2での条件付きPUTや障害復旧まで検証した結果ではない。更新メタデータ・256分割・世代保持・未送信バッファは別途見積もる。

検証にはDuckDB 1.5.5を使用した。サンプル、測定結果、調査用スクリプトはGit管理外のローカル調査データとして保管する。

## 費用と移行時の変更

[R2 Standardの料金](https://developers.cloudflare.com/r2/pricing/)は容量$0.015/GB月、10GB月が無料。Class Aは100万回/月まで無料で超過$4.50/100万回、Class Bは1,000万回/月まで無料で超過$0.36/100万回。無料枠は同一アカウントの他用途と共有し、課金単位の切り上げがある。

保存容量が合計20GB月なら容量分は$0.15。これは運用全体の容量予測ではなく料金例。ファイルを5,000ページずつまとめられれば、100万ページの更新のデータPUTは約200回になる。時間・容量による早期送信、完了印、スナップショット、一覧取得、再試行の操作は別に数える。1ページ1ファイルに比べて操作数を抑えやすい。

実装時はリンク書き込みに加えて、現在linksを直接読む巡回補充とグラフ集計を切り替える。巡回候補は発見時にURL台帳へ記録する経路へ寄せ、既存リンク先の収録漏れをバックフィル・検証する。補充候補の集合やサイトの多様性が変わる点は、元SQLとの比較で確認する。大規模なPageRankのメモリ使用は別の課題であり、保存形式の変更だけで解決すると扱わない。

初回移行は、全書き手を停止した境界で送信待ち記録へ切り替え、旧linksを固定したベースラインとして分割出力する方法が分かりやすい。旧表を固定した後の更新はrevision>0のbatchへ保存し、revision=0のベースラインに適用する。切替後も旧表へ書くワーカーや移行時点の処理途中ジョブを残さない。旧表を読むジョブを調整し、復元検証と新経路の検証が済んでから旧表の撤去を別の切替手順で行う。

この案の次の実装対象は、共通レコード、短期送信待ち、アップローダー、スナップショット作成、読み出し用の小さなCLI。R2バケット作成、全件移送、本番の切替・削除は今回実施していない。
